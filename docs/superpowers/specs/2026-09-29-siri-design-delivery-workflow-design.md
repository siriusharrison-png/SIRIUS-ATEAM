# Siri 设计交付工作流 — 设计文档

**日期**：2026-09-29
**状态**：待评审
**作者**：转转 + 小的

---

## 1. 背景与目标

转转（设计师）的日常工作流：产品通过飞书 PRD + Linear issue 分发任务 → 分析需求、对应项目做设计 → 产生 Figma / PR / 代码分支 / Vercel 关联 → 交付时关联设计 PRD 推送到业务群完成交付。

当前痛点：
- 任务来源分散（群消息 / PRD / issue），缺少统一归档
- 缺少一个盯着优先级的待办视图
- 对外产出（关联信息、交付）没有统一的卡片形态
- 历史交付、历史澄清过的问题无法快速检索
- 设计文档（评审 / 说明）产出无规范、无模板

**目标**：配一套围绕飞书机器人「Siri」的设计交付工作流，覆盖任务归档、待办提醒、关联登记、交付验收、状态流转、历史问答，并配套两类设计文档的产出能力。

---

## 2. 核心定位与边界

**Siri 是"安排任务的人"**：对外发布信息、收集信息、回答问题。**真实设计工作由转转和团队完成，Siri 不做设计、不写文档。**

系统分三块，可独立交付：

| 模块 | 职责 | 位置 |
|------|------|------|
| **Siri 机器人** | 编排 / 推送 / 归档 / 历史问答 / 意图理解 | `agents/siri/` |
| **文档能力** | 评审 / 说明两类文档的模板 + 产出 skill | `docs/design-delivery/` |
| **任务台账** | 任务数据持久化 | 飞书多维表格（存储层可替换） |

**关键分界 —— 智能来源分两处，不要混淆**：
- **文档产出**（重）：在项目环境由小的（Claude）产出，能读真实代码 / 分支 / Figma，结合 Astra 标准。质量优先。**Siri 不碰文档生成。**
- **Siri 意图理解**（轻）：Siri 靠自然语言理解你的意图（"这个以前做过吗""帮我归档""可以交付了"），是轻量意图识别，不是写文档。

## 3. 架构

```
                     飞书自建应用「Siri」
                            │
          ┌─────────────────┼─────────────────┐
          │ 事件回调         │ Vercel Cron      │
          ▼                 ▼                  │
   ┌──────────────┐  ┌──────────────┐          │
   │ 回调 Function │  │ 定时 Function │          │
   │ (@Siri/动态) │  │ (10:00/18:00)│          │
   └──────┬───────┘  └──────┬───────┘          │
          │                 │                  │
          ▼                 ▼                  │
   ┌────────────────────────────────┐          │
   │      意图理解 + 编排层          │          │
   │  (Claude API 轻量意图识别)      │          │
   └────────┬───────────────────────┘          │
            │                                   │
   ┌────────┼──────────┬──────────┬─────────┐  │
   ▼        ▼          ▼          ▼         ▼  │
 飞书API  Linear API  GitHub API Vercel API 存储层
 (读写)   (读写)      (只读)     (只读)     (飞书表格)
```

**运行形态**：Vercel Functions（无状态）+ Vercel Cron（定时）。全在 Vercel 一个生态，复用现有 Vercel 账号。

**权限范围**（全部转转个人账号）：

| 平台 | 权限 | 用途 |
|------|------|------|
| 飞书 | 读写 | 收事件、发卡片、读写多维表格 |
| Linear | 读写 | 查重复需求、建 / 改 issue |
| GitHub | 只读 | 拉 PR 信息填卡片 |
| Vercel | 只读 | 拉部署地址 / 状态填卡片 |

## 4. 数据模型 — 飞书多维表格任务台账

存储层封装成一层接口（`store.read` / `store.write` / `store.query`），当前实现用飞书多维表格，不顺后续换 Vercel Postgres 只改这一层。

**任务表字段**（非全必填）：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| 需求名 | 文本 | 是 | 任务标题 |
| 来源 | 单选 | 否 | 群 / PRD / issue |
| Linear issue | 链接 | 否 | issue URL / 编号 |
| Figma | 链接 | 否 | 手动提供 |
| PR | 链接 | 否 | 产出时对应 |
| 分支 | 文本 | 否 | 代码分支名 |
| Vercel | 链接 | 否 | 部署地址 |
| 状态 | 单选 | 是 | 见状态流转 |
| 优先级 | 单选 | 否 | 高 / 中 / 低（有明确优先级才提示） |
| 设计 PRD | 链接 | 否 | 交付时关联 |
| 更新时间 | 时间 | 自动 | 每次变更刷新 |

**状态流转**（6 阶段，两个关键交付节点）：

```
需求澄清 → 立项评审 → 设计 → 设计评审 → 待验收 → 完成
              ↑                    ↑
        需求文档 + issue 节点   设计交付节点
                              (分支 / Figma / 设计稿 / 文档)
```

## 5. Siri 能力（自然语言驱动）

Siri 通过意图理解响应自然表达，不依赖固定指令词。核心能力：

| 能力 | 触发（自然语言示例） | 行为 |
|------|---------------------|------|
| **归档** | "帮我把这个需求记一下""归档一下麦迪发的任务" | 解析信息 → 建表记录（状态默认「需求澄清」） |
| **关联登记** | "这个需求的 Figma 是 xxx""PR 出来了 xxx" | 绑定链接到对应任务 |
| **历史问答** | "这个以前做过吗""历史交付里有没有类似的" | 查表 → 回答（含历史交付、历史澄清） |
| **issue 查重** | （建 issue 前自动执行） | 先查 Linear 有无类似需求，无则新建 |
| **交付** | "这个可以交付了" | 组交付卡片 → 推转转个人群验收 → 确认后推业务群 |
| **状态流转** | "这个进入设计评审了""改到待验收" | 更新状态字段 |

**交付两步走**（关键流程）：
```
"可以交付了" → Siri 组装交付卡片 → 推转转个人群
                                        ↓
                              转转验收 → 确认无误
                                        ↓
                              Siri 推送到指定业务群 → 状态置「完成」
```

## 6. 卡片规范

对外产出统一走固定卡片形态。两种核心卡片：

### 6.1 Todo 卡片（定时推 10:00 / 18:00 北京时间，仅转转个人群可见）

```
┌─────────────────────────────────┐
│ 📋 今日待办 · 09-29 10:00         │
├─────────────────────────────────┤
│ 🔴 高  [需求名]  设计评审          │
│         Figma · PR · Vercel       │
│ 🟡 中  [需求名]  设计中            │
│ ⚪ —   [需求名]  需求澄清          │
├─────────────────────────────────┤
│ 共 N 项 · 高优 M 项               │
└─────────────────────────────────┘
```
- 按优先级排序，有明确优先级的项高亮提示
- 关联链接以图标 + 短链呈现

### 6.2 交付卡片（先推个人群验收，确认后推业务群）

```
┌─────────────────────────────────┐
│ ✅ 交付 · [需求名]                │
├─────────────────────────────────┤
│ 需求来源：[PRD 链接]              │
│ Linear：  [issue]                 │
│ 设计稿：  [Figma]                 │
│ 代码：    [PR] · [分支]           │
│ 预览：    [Vercel]                │
│ 设计文档：[评审 / 说明文档]        │
├─────────────────────────────────┤
│ 待验收 → 确认后推送业务群          │
└─────────────────────────────────┘
```
- 字段缺失时该行省略（非全必填）

**其他动态推送**（交付验收结果、状态变更提示）按事件实时推，非定时。

## 7. 文档产出能力（独立模块，依赖 Astra + skill）

在项目环境由小的产出，非 Siri 生成。两类文档：

### 7.1 设计评审文档
- **场景**：需求到评审对齐阶段
- **内容**：从需求到改动，澄清功能与流程，可演示
- **特点**：**允许 TODO / 待讨论项**，服务于对齐讨论

### 7.2 设计说明文档
- **场景**：需求和评审对齐后，按当前设计分支交付
- **内容**：简洁准确描述设计改动 + 交互流程，含流程图
- **特点**：**只陈述结果**，不反复澄清历史问题、不带过程讨论 / 过程思考

**实现**：`docs/design-delivery/templates/` 放两套模板；配一个产出 skill，产出时读真实代码 / 分支 / Figma，结合 Astra 六维标准（Clarity / Refinement / Responsiveness / Composability / Generativity / Criticality）。流程图用 Mermaid。

## 8. 定时任务

| 时间（北京时间） | 任务 |
|------------------|------|
| 10:00 | 推 Todo 卡片到个人群 |
| 18:00 | 推 Todo 卡片到个人群 |

用 Vercel Cron 实现。Vercel Hobby 版 Cron 每天两次触发在限额内。若定时不好做可删除，不影响主体功能。

---

## 9. 凭证与安全

- 所有 API token 为转转个人账号，存 Vercel 环境变量（不进代码库）
- 飞书事件回调需校验签名（防伪造请求）
- 存储层不记录敏感内容原文，只存任务元数据与链接

---

## 10. 交付边界（本 spec 覆盖范围）

**包含**：
- Siri 机器人（Vercel Functions + Cron + 飞书回调 + 意图理解 + 多平台 API + 存储层）
- 飞书多维表格任务台账结构
- Todo 卡片、交付卡片规范
- 两类设计文档的模板 + 产出 skill

**不包含（后续可扩展）**：
- 产品 / 其他角色使用 Siri（当前只服务转转）
- 存储层换 Postgres（先用飞书表格，接口已预留）
- 展示页加 Siri 团队成员卡片（叙事层，非核心）

---

## 11. 分期建议

考虑到系统涉及多平台集成，建议分期，每期可独立验证：

- **一期（骨架）**：飞书应用 + Vercel 回调打通，@Siri 能收到消息并回一句话。验证常驻链路。
- **二期（归档 + 台账）**：飞书多维表格 + 存储层 + 归档 / 关联 / 状态流转。验证数据闭环。
- **三期（卡片 + 定时）**：Todo 卡片 + 交付卡片 + Vercel Cron 定时推送。验证对外产出。
- **四期（多平台 + 历史问答）**：Linear / GitHub / Vercel API 接入 + issue 查重 + 历史问答。验证智能编排。
- **文档能力**：与上面并行，独立交付（模板 + skill）。

每期完成后进入下一期前评估是否调整。
