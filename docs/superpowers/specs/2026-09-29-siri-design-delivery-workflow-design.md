# Siri 设计交付工作流 — 设计文档

**日期**：2026-09-29（架构重写 2026-09-30）
**状态**：待评审
**作者**：转转 + 小的

---

## 1. 背景与目标

转转（设计师）的日常工作流：产品通过飞书 PRD + Linear issue 分发任务 → 分析需求、对应项目做设计 → 产生 Figma / PR / 代码分支 / Vercel 关联 → 交付时关联设计 PRD 推送到业务群完成交付。转转日常在不同项目里用 Claude 工作。

当前痛点：
- 任务来源分散（群消息 / PRD / issue），缺少统一归档
- 缺少一个盯着优先级的待办视图
- 对外产出（关联信息、交付）没有统一的卡片形态
- 历史交付、历史澄清过的问题无法快速检索
- 设计文档（评审 / 说明）产出无规范、无模板

**目标**：配一套以**共享任务台账（飞书多维表格）为中心**的设计交付工作流，由飞书智能伙伴「Siri」常驻服务（推送、答问、对外代理），Claude 按需协作（登记连接、生成文档、触发 Siri），覆盖任务归档、待办提醒、关联登记、交付验收、状态流转、历史问答，并配套两类设计文档的产出能力。

## 2. 核心定位与边界

### 2.1 三个角色，一个中心

**中心 = 共享任务台账（飞书多维表格）。** 它是整个系统的唯一真相源：任务台账、Siri 推送的数据源、Claude 写入连接的落点、未来他人查看设计侧进度的窗口。Siri 和 Claude 都不是主角，那张表才是——两者都只是它的读写者。

| 角色 | 定位 | 运行形态 |
|------|------|----------|
| **共享任务台账** | 唯一真相源，所有状态汇聚于此 | 飞书多维表格 |
| **Siri**（飞书智能伙伴） | 对外发布 / 收集 / 回答的"设计侧代理"，常驻服务 | 飞书智能伙伴平台（Aily），云端常驻 |
| **Claude**（小的） | 设计 / 编排大脑，按需协作 | 项目环境，转转唤起时运行，不常驻 |

```
        转转（唯一决策者 / 唤起者）
         ╱                        ╲
   Claude（小的）              Siri（飞书智能伙伴）
   按需 · 设计编排              常驻 · 执行服务
   ─────────                  ─────────
   • 想清楚要什么               • 收发消息、被@自动答
   • 写技能描述文案             • 定时推送（前瞻/回顾）
   • 写设计文档                 • 连 GitHub / Linear
   • 通过飞书 API 读写表格      • 生成飞书卡片
   • 触发 Siri 做事             • 对外代理（他人查进度/找文档）
         ╲                        ╱
          ▼                      ▼
        ┌────────────────────────┐
        │  共享任务台账（多维表格）  │ ← 唯一真相源
        └────────────────────────┘
```

### 2.2 Siri 的职责与边界

**Siri 是"设计侧代理 / 安排任务的人"**：对外发布信息、收集信息、回答问题。**真实设计工作由转转和团队完成，Siri 不做设计、不写设计文档。**

### 2.3 关键分界 —— 智能来源分两处，不要混淆

- **文档产出**（重）：在项目环境由小的（Claude）产出，能读真实代码 / 分支 / Figma，结合 Astra 标准。质量优先。**Siri 不碰设计文档生成。**
- **Siri 意图理解**（轻）：Siri 靠自然语言理解意图（"这个以前做过吗""帮我归档""可以交付了"），生成卡片、读写表格、推送。是平台内建的轻量意图识别，不是写文档。

### 2.4 一个诚实的约束

**Claude 不常驻**——转转不主动唤起，Claude 不会自行运行。因此"转转在项目里说话 → Claude 触发 Siri"这条链的触发点始终是转转开口。反之 **Siri 常驻**（定时推送、群里被@自动答），这些不需要 Claude。分工是：**日常主动服务靠 Siri，复杂设计 / 编排靠转转唤起 Claude**。

### 2.5 日常协作协议 —— Claude 产出「可直接发给 Siri 的指令」

在飞书 API 触发脚本落地前（甚至落地后，作为人工兜底通道），转转与 Siri 之间**没有自动化直连**，转转是唯一的中转人。为了不让转转做"翻译"的苦活，约定：

**每当转转说"我需要 Siri 做 XX"（发布任务 / 归档 / 关联登记 / 交付 / 查历史等），Claude 必须直接产出一段转转可以原样复制、粘贴发给 Siri 的自然语言指令**，而不是只讨论方案或给抽象描述。

指令要满足：
- **可直接复制**：单独一段话，转转不需要再编辑或补充信息就能发送（除非确实缺转转才知道的信息，如具体链接）
- **贴合 Siri 已验证的理解方式**：参照 §5 已跑通的归档技能交互（自然语言描述场景 + 字段），不用固定指令词
- **信息完整**：Claude 已知的信息（需求名、链接、状态等）直接写入指令，不留给 Siri 猜或转转补

**示例**（沿用已跑通的归档技能）：转转说"帮我用 Siri 归档一下这个价格改造需求，PR 是 xxx，分支是 yyy"→ Claude 直接回复一段可复制的话，例如：「帮我归档一个需求：价格改造，来源是我主动发起，PR 链接 xxx，分支 yyy，状态设为需求澄清。」转转复制发给 Siri 即可，不用自己拼句子。

这个协议在 §12 各期都适用，是当前（触发脚本落地前）的主要协作方式。

## 3. 架构

### 3.1 以共享表格为中心的读写模型

```
   转转在任意项目里唤起 Claude
   （"归档这个任务" / "该交付了" / "生成评审文档"）
              │
              ▼
   ┌──────────────────────┐
   │  Claude（项目环境）    │
   │  设计 / 编排 / 写文档   │
   └──────────┬───────────┘
              │ 调飞书开放平台 API（可复用触发脚本）
       ┌──────┴────────┐
       ▼               ▼
  读写共享表格      发消息@Siri 触发其技能
       │               │
       ▼               ▼
   ┌────────────────────────┐         ┌─────────────────────┐
   │  共享任务台账（多维表格）  │◀───────▶│  Siri（飞书智能伙伴）  │
   │      唯一真相源          │  读写   │  常驻执行             │
   └────────────────────────┘         └──────────┬──────────┘
              ▲                                   │
              │ 读                                 ▼
        他人（未来）                     • 定时推送（前瞻10:00/回顾18:30）
        通过 Siri 查进度/找文档            • 群里被@自动答
                                        • 组卡片推送到指定群
                                        • 连 GitHub / Linear
```

### 3.2 运行形态

- **Siri**：飞书智能伙伴平台（Aily）云端常驻。平台已内建：收发消息、被@响应、定时推送（每日前瞻 / 每日回顾 / 每周回顾）、连接器（GitHub / Linear）、飞书卡片生成、工作上下文记忆、主动程度控制。**无需自建服务器 / Vercel Functions。**
- **Claude 侧触发脚本**：`~/Desktop/siri-tools/siri.sh`（独立仓库 `github.com/siriusharrison-png/siri-tools`，2026-09-30 已实现并实测通过），任意项目里的 Claude 会话都能 `bash` 调用。子命令：`fields` / `list` / `archive` / `update` / `delete` / `chats` / `send`。凭证独立存于 `~/.config/siri/.env`（本机专属路径，不在任何 git 仓库内），与脚本本体分离。用法详见该仓库 `README.md`。
- **Siri 能力扩展**：通过平台的「技能」实现（对话创建，或上传 .skill 文件 / 文件夹）。技能是带描述 + 逻辑 + 资源（如卡片模板）的能力包。Claude 负责写技能描述文案，转转喂给 Siri 生成 / 上传。

### 3.3 Vercel 自建方案的退场说明

早期设计（2026-09-29 初版）拟用 Vercel Functions + Cron 自建飞书应用作为 Siri 主体。2026-09-30 发现转转已有飞书智能伙伴平台 agent，平台原生提供了收发消息、定时、连接器、卡片生成等全部骨架能力，**Vercel 自建方案作废**。对应的一期骨架计划（`docs/superpowers/plans/2026-09-29-siri-phase1-skeleton.md`）随之废弃，不再执行。

### 3.4 权限与凭证概览

| 平台 | 谁用 | 权限 | 用途 |
|------|------|------|------|
| 飞书开放平台（自建应用） | **Claude 侧脚本** | 读写 | 读写多维表格、发消息触发 Siri |
| 飞书（Siri 平台连接器） | Siri | 读写 | 收发消息、发卡片、读写多维表格 |
| GitHub | Siri（连接器） | 读（PR / issue / 仓库） | 拉 PR 信息、完成对账 |
| Linear | Siri（连接器） | 读写 | 查重复需求、建 / 改 issue |
| Vercel | 无原生连接器 | — | 部署地址：转转交付时提供（优先探索自动获取方式，不行则手动贴入指令 / 表格） |

凭证细节与获取方式见第 9 节。

## 4. 数据模型 — 共享任务台账（飞书多维表格）

这是系统的中心。表结构必须**规整、自解释**——因为未来会开放给更多人查看（见 §10 场景 3），别人不看说明也应能读懂每条记录的状态与内容。

**任务表字段**（非全必填）：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| 需求名 | 文本 | 是 | 任务标题 |
| 来源 | 单选 | 否 | 产品PRD / 主动发起 / issue / 群消息 |
| Linear issue | 链接 | 否 | issue URL / 编号（承担 spec 早期"设计 PRD"的角色，不单独设字段） |
| Figma | 链接 | 否 | 手动提供 |
| PR | 链接 | 否 | 产出时对应 |
| 代码分支 | 文本 | 否 | 代码分支名 |
| Vercel | 链接 | 否 | 部署地址 |
| 状态 | 单选 | 是 | 严格 6 阶段，见状态流转（不设"已搁置"，搁置的任务另行处理） |
| 优先级 | 单选 | 否 | 高 / 中 / 低（有明确优先级才提示） |
| 归档时间 | 时间 | 自动 | 首次归档时间 |
| 设计文档 | 链接 | 否 | 评审 / 说明文档链接（供历史检索、对外查阅，2026-09-30 已建） |

**更新时间**：不单独设字段，使用飞书多维表格自带的"最后修改时间"。

**状态流转**（6 阶段，两个关键交付节点）：

```
需求澄清 → 立项评审 → 设计 → 设计评审 → 待验收 → 完成
              ↑                    ↑          ↑        ↑
        需求文档 + issue 节点   设计交付节点  联调后   issue=done
                              (分支/Figma/    (研发    (客观依据:
                               设计稿/文档)    联调后    Linear issue
                                              测试验收) done 状态)
```

**流程不是单向死流程，允许非线性进入与回退**：
- **入口灵活**：任务可能没有正式需求（直接被提 issue、或群里一句话、或转转主动发起），此时从任意状态进来后**倒回补齐「需求澄清」**。来源字段区分产品 PRD / 主动发起 / issue / 群消息。
- **产物持续变化**：设计过程与交付后都会有多次沟通确认，所以 **PR / 分支 / 存档文档不是一次性定稿，会持续迭代**，直到交付完成并顺利上线。存档文档以「可迭代版本」对待，不是快照。
- **「完成」的客观判定**：读 Linear issue 状态，issue 置 done 即判定完成，不靠主观判断。「待验收」发生在研发**联调之后**（测试对照设计文档验收）。

**已对齐（2026-09-30）**：Siri 首个归档技能生成的表原为「需求澄清 / 设计中 / 开发中 / 已完成 / 已搁置」5 档，与本 spec 不一致，已通过 Claude 侧 API 直接修正为本节的严格 6 阶段（不设"已搁置"）。同时修正「来源」选项重复项、新增「设计文档」字段。

## 5. Siri 能力（自然语言驱动，技能形式落地）

Siri 通过意图理解响应自然表达，不依赖固定指令词。每个能力对应平台上的一个技能（Claude 写描述文案，转转喂给 Siri 生成）。核心能力：

| 能力 | 触发（自然语言示例） | 行为 | 实测状态 |
|------|---------------------|------|----------|
| **归档** | "帮我把这个需求记一下" | 解析信息 → 建表记录（状态默认「需求澄清」）；缺需求名则追问 | ✅ 已跑通 |
| **关联登记** | "这个需求的 Figma 是 xxx""PR 出来了" | 绑定链接到对应任务 | 待建 |
| **状态流转 / 更新** | "这个进入设计评审了""改到待验收" | 更新已有记录的状态 / 字段 | 待建（归档技能暂只新增，不更新） |
| **历史问答** | "这个以前做过吗""历史交付里有没有类似的" | 查表 → 回答（含历史交付、历史澄清、文档链接） | 待建 |
| **issue 查重** | （建 issue 前自动执行） | 先查 Linear 有无类似需求，无则新建 | 待建 |
| **交付** | "这个可以交付了" | 组交付卡片 → 推转转个人群验收 → 确认后推业务群 | 待建 |
| **完成对账** | （检测到 Linear issue = done 时） | 回读 PR + 分支，校对存档文档与实际代码一致、最新；不一致则提示更新 | 待建 |

**交付两步走**（关键流程）：
```
"可以交付了" → Siri 组装交付卡片 → 推转转个人群（仓鼠跑轮）
                                        ↓
                              转转验收 → 确认无误
                                        ↓
                              Siri 推送到指定业务群 → 状态置「完成」
```

## 6. 卡片规范

对外产出统一走固定卡片形态。两种核心卡片：

### 6.1 Todo 卡片（定时推 10:00 / 18:00 北京时间，仅转转个人群「仓鼠跑轮」可见）

```
┌─────────────────────────────────┐
│ 📋 今日待办 · 09-30 10:00         │
├─────────────────────────────────┤
│ 🔴 高  [需求名]  设计评审          │
│         Figma · PR · Vercel       │
│ 🟡 中  [需求名]  设计中            │
│ ⚪ —   [需求名]  需求澄清          │
├─────────────────────────────────┤
│ 共 N 项 · 高优 M 项               │
└─────────────────────────────────┘
```
- 按优先级排序，有明确优先级的项高亮提示
- 数据源为共享表格中"未完成 / 未更新"的任务
- 关联链接以图标 + 短链呈现

### 6.2 交付卡片（先推个人群验收，确认后推业务群）

```
┌─────────────────────────────────┐
│ ✅ 交付 · [需求名]                │
├─────────────────────────────────┤
│ 需求来源：[PRD 链接]              │
│ Linear：  [issue]                 │
│ 设计稿：  [Figma]                 │
│ 代码：    [PR] · [分支]           │
│ 预览：    [Vercel]                │
│ 设计文档：[评审 / 说明文档]        │
├─────────────────────────────────┤
│ 待验收 → 确认后推送业务群          │
└─────────────────────────────────┘
```
- 字段缺失时该行省略（非全必填）

**其他动态推送**（交付验收结果、状态变更提示）按事件实时推，非定时。

## 7. 文档产出能力（独立模块，依赖 Astra + skill）

在项目环境由小的产出，非 Siri 生成。两类文档：

### 7.1 设计评审文档
- **场景**：需求到评审对齐阶段
- **内容**：从需求到改动，澄清功能与流程，可演示
- **特点**：**允许 TODO / 待讨论项**，服务于对齐讨论

### 7.2 设计说明文档
- **场景**：需求和评审对齐后，按当前设计分支交付
- **内容**：简洁准确描述设计改动 + 交互流程，含流程图
- **特点**：**只陈述结果**，不反复澄清历史问题、不带过程讨论 / 过程思考

### 7.3 文档的真实用途 —— 跨职能协作依据

这两类文档不是自说自话的交付描述，而是**给下游同事用的工作依据**：
- **研发确认联调**：功能说明 / 交互说明让研发对照实现，确认联调点
- **测试对应验收**：测试按文档逐项验收，对齐「做到什么程度」

**历史案例**（转转已产出过的对应文档形态）：sandbox 相关、价格改造相关、apikey 设计相关，以及若干页面结构 / 功能优化相关。这些是文档模板要参照的真实样本 —— 好的功能说明 / 交互说明文档能直接支撑研发联调与测试验收。

**文档链接落表**：产出的文档链接写入共享表格「设计文档」字段，供历史检索与对外查阅（§10 场景 3 别人通过 Siri 找历史文档，即查此字段）。

**完成对账**：issue 置 done 后，Siri 回读 PR + 分支，校对存档文档与实际提交的代码信息一致、最新；发现不一致则提示转转更新文档，确保定稿文档反映最终代码。

**文档规范可迭代**：本节 7.1 / 7.2 的类型与结构是初版，在实际使用中逐步调整优化，不是一次定死。

**实现**：`docs/design-delivery/templates/` 放两套模板；配一个产出 skill，产出时读真实代码 / 分支 / Figma，结合 Astra 六维标准（Clarity / Refinement / Responsiveness / Composability / Generativity / Criticality）。流程图用 Mermaid。模板设计时参照上述历史案例的实际结构。

## 8. 定时任务（平台原生）

Siri 平台内建定时框架（每日前瞻 / 每日回顾 / 每周回顾），直接承载 Todo 推送，无需自建 cron：

| 平台机制 | 时间（北京时间） | 承载任务 |
|----------|------------------|----------|
| 每日前瞻 | 工作日 10:00 | 推 Todo 卡片到个人群 |
| 每日回顾 | 18:30（可调至 18:00） | 推 Todo 卡片到个人群 |

主动推送程度设为「克制」档，尊重免打扰时段（22:00–08:00）。

## 9. 凭证与安全

### 9.1 需要转转提供的凭证（供 Claude 侧触发脚本使用）

为让 Claude 能读写共享表格、发消息触发 Siri，需要一个**飞书自建应用**（角色是「Claude 伸进飞书的手」，不是 Siri 本身）：

| 凭证 | 来源 | 用途 |
|------|------|------|
| App ID | 飞书开放平台 → 自建应用 | 换取 access token |
| App Secret | 同上 | 换取 access token |
| 多维表格 app_token | 目标多维表格的 URL / 分享 | 定位任务台账 |
| 表格 table_id | 同上 | 定位具体数据表 |
| Siri 的 chat/接收标识 | 触发消息的目标 | 发消息 @Siri 触发技能 |
| 目标群标识（仓鼠跑轮 / 业务群） | 群设置 | 卡片推送目标 |

**获取方式与逐步指引在落地时提供**（转转 review 本 spec 后，一起看如何一步步拿到并安全存放）。

### 9.2 安全约束

- 所有凭证存本地环境变量 / `.env`（已在 `.gitignore`），**绝不进代码库**
- Claude 不登录转转的企业账号、不碰企业内网鉴权；凭证仅用于飞书开放平台 API 调用
- 触发脚本只读写授权范围内的表格与消息，不做越权操作
- 表格对外开放（§10 场景 3）时，需评估哪些字段 / 状态对外可见（如「待讨论」草稿是否露出），此项三期细化

## 10. 目标场景（验证架构）

以下三个场景验证「共享表格中心」架构满足预期：

**场景 1：建分支 → 存连接 → 让 Siri 推送**
转转在项目里建分支、推送 → 告诉 Claude 分支 / PR 等链接 → Claude 写入表格对应记录并触发 Siri → Siri 组交付卡片，先推仓鼠跑轮验收，确认后推指定群。转转不手动填表。

**场景 2：查 Todo，Siri 推送待办**
别人建的任务久未更新 → Siri 常驻读表，定时（10:00/18:30）筛出未完成 / 未更新项，按优先级组 Todo 卡片推到仓鼠跑轮。**此场景 Siri 完全自主，不需 Claude。** 转转也可随时在飞书 @Siri 查待办。

**场景 3：表格开放给更多人，Siri 成为设计侧代理**
表格权限开给团队 → 他人通过 Siri 查看转转的进度、当前任务项、检索历史相关文档。这要求：表结构规整自解释、文档链接落表可检索、对外可见性经过评估。

## 11. 交付边界（本 spec 覆盖范围）

**包含**：
- 共享任务台账（飞书多维表格）结构，对齐 6 阶段状态
- Siri 技能集（归档 / 关联 / 状态更新 / 交付两步走 / 历史问答 / issue 查重 / 完成对账）的描述文案
- Claude 侧飞书 API 触发脚本（读写表格 + 发消息触发 Siri），可复用于任意项目
- Todo 卡片、交付卡片规范
- 两类设计文档的模板 + 产出 skill
- 平台配置对齐（伙伴档案、定时、主动程度、目标群）

**不包含（后续可扩展）**：
- 存储层换其他数据库（先用飞书表格）
- 表格对外开放的细粒度权限与可见性策略（场景 3 落地时细化）
- 展示页加 Siri 团队成员卡片（叙事层，非核心）
- Vercel 原生连接器（平台无，交付地址暂手动提供）

## 12. 分期建议

以「共享表格中心」重新分期，每期可独立验证：

- **一期（表格 + 归档）**：✅ 共享表格结构已对齐 6 阶段状态；归档技能已跑通。剩余：关联登记 / 状态更新技能。验证数据闭环。
- **二期（Claude 触发脚本）**：✅ `siri.sh` 已实现并实测通过（token/fields/list/archive/update/delete/chats/send）。Claude ↔ 表格 ↔ Siri 链路已验证。
- **三期（卡片 + 定时）**：Todo 卡片 + 交付卡片（交付两步走）+ 平台定时推送对齐。验证对外产出。
- **四期（历史问答 + 对账 + 对外代理）**：历史问答 + issue 查重 + 完成对账 + 表格对外开放（场景 3）。验证智能编排与对外服务。
- **文档能力**：与上面并行，独立交付（模板 + skill）。

归档技能已实测跑通，一期起点较高。每期完成后进入下一期前评估是否调整。
